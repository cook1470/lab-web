# 判準（動手前寫死，2026-09-18）

三條都要在動手**之前**定好門檻，量出來不合格就是不合格，不事後改數字。
（若真的要改判準，必須在 RESULT.md 明寫「改了什麼、為什麼」——偷偷改才是錯。）

## ① 四層視差速度確實不同，且遠景最慢
**量法**：`window.__probe.parallax()` 回傳四層在相機位移 1000 世界單位時各自的畫面位移。
**門檻**：
- `d1 < d2 < d3 < d4`，且**每一層之間至少差 0.10 倍相機速度**（避免「數字不同但眼睛看不出來」）。
- 第 3 層（角色所在地面）速度 = 1.00×（角色踩在上面，必須跟相機同步，否則腳會漂）。
- 第 1 層 ≤ 0.20×。

**能證明它錯的方法**：兩張不同相機位置的截圖，遠景天際線在畫面上的位移必須肉眼小於地面裂縫的位移。

## ② 角色在任何一層背景前都看得見
**量法**：`window.__probe.contrast()` — 把角色移到 N 個取樣點（每個點的背後分別是天空、遠景大樓、中景廢墟、平台、前景物），
各畫兩幀（有角色／無角色），取角色剪影覆蓋的像素，比較「剪影亮度」與「同位置背景亮度」的相對亮度（WCAG relative luminance）。
**門檻**：
- 每個取樣點的**中位數對比度 ≥ 3.0:1**（WCAG 非文字圖形的最低可辨識線）。
- **最差的單一取樣點 ≥ 2.5:1**（不允許某一層把角色吃掉）。
- 前景層允許壓在角色前，但**不得遮住角色剪影面積的 35% 以上**（量遮蔽率）。

**這條的存在理由**：規格裡黑白版的病就是「主角跟背景搶同一個黑」。純黑只給角色，背景最深只到深灰——
這條判準就是在驗那條規矩有沒有被我自己違反。

## ③ 手機橫式 60fps 不掉
**量法**：`window.__probe.perf()` — 在 844×390（iPhone 橫式）下，讓相機持續移動，記錄連續 180 幀的 frame time。
**門檻**：
- **中位數 frame time ≤ 16.7ms**。
- **p95 ≤ 20ms**（允許偶發，但不允許常態掉幀）。
- 不用 requestAnimationFrame 的實際間隔判定（那會被 vsync 綁死），量的是**每幀的繪製工作量**（draw 函式自身耗時），
  門檻另訂：**繪製工作 p95 ≤ 8ms**（留一半預算給瀏覽器合成）。

## 不在判準內（明說）
- 不做玩法、敵人、UI 文字堆。這是一張會動的畫面。
- 「像不像參考圖」不是判準，是主觀項，寫進 RESULT.md 的「最不像的地方」。

# v2 增訂（2026-09-18，製作人看過 v1 之後）

製作人給了三件事（遠近同色、天空沒有光源、前景只是一條暗帶）。
v1 的三條判準**全部沿用、門檻不得放寬**，另外增訂兩條。

## ①-b 遠景與中景的明度差（新增）

**為什麼要這條**：v1 的遠景與中景都是紫、只差一點點暗度，深度出不來。
而「看起來像不像兩層」是個主觀詞，得先變成一個量得到的東西。

**量法**：`window.__probe.layerLuma()`。同一個相機位置畫三幀（完整／關掉層1／關掉層2），
用像素差認出「哪些像素是層1 的、哪些是層2 的」，各取平均 WCAG 相對亮度。

**門檻**：`(L_far + 0.05) / (L_mid + 0.05) ≥ 2.0`。

**2.0 的理由**：兩塊大面積的平塗色，比值到 2:1 左右才會被讀成「兩個不同的調子」而不是「同色的深淺」。
這是先寫的數字，不是量完再湊的——v2 第一次量出 **1.99**，**我改的是畫面（遠景再往天空的橘紅推一階），不是門檻**。

**這條上量出的一個我自己的錯**：薄霧本來寫在 `drawFar()` 裡，
於是「關掉層1」會連霧一起關，霧底下的天空全被算成層1 的像素——
farPx 從 74 萬膨脹到 114 萬，明度差被稀釋成 1.80。
霧是大氣不是天際線，拆成獨立的 `drawHaze()` 之後才是 3.58。
**尺量到的東西是我自己放進去的，第 N 次。**

## ②-v2 前景遮蔽：改判準的形狀（修訂，附理由）

**v1 寫的是**「前景不得遮住角色剪影 35% 以上」。
**v2 要求前景變成有實體、會從角色前方掠過的東西**，這跟一個單一的遮蔽上限直接衝突。

**改的理由**：35% 這個數字回答的是「遮多少」，但真正要問的是
**「玩家還找不找得到角色」**。而人找角色靠的是**頭跟那顆白眼睛**，不是小腿。
所以把一個數字換成三條，各自回答不同的事：

| 新門檻 | 回答的問題 |
|---|---|
| 單張最大遮蔽 **≤ 45%**（放寬自 35%） | 前景有沒有實體 |
| **頭部遮蔽 ≤ 25%**（新增，取剪影最上方 60 世界單位） | 玩家還定位得到角色嗎 |
| 遮蔽 > 25% 的取樣點 **≤ 1/3** | 前景是「掠過」還是「常駐擋著」 |

**對比度那兩條（中位數 ≥3.0、最差取樣點 ≥2.5）原封不動**——那是不准退步的部分。

## ③ 不變
沿用 v1。真實幀間隔中位數 ≤16.7、p95 ≤20；繪製工作 p95 ≤8（且仍記得這條比尺的噪音還細）。

# v3 增訂（2026-09-18，製作人看過 v2 之後）

製作人三件：受光邊全拿掉、加真的要跳的東西、兩套配色。
**v1／v2 的判準全部沿用、門檻不得放寬**，另外增訂三條。

## ①-b 修訂：改用固定色階量（門檻不變）

受光邊拿掉之後，**深度只剩「各層固定的明度差」**在撐。
判準①-b 的門檻維持 `(L_far + 0.05) / (L_mid + 0.05) ≥ 2.0`，
但量的東西現在是純粹的固定色階（畫面上已經沒有任何隨相機／太陽方位變化的明暗）。
**兩套配色都要各自過這條**，不是只有預設那套。

## ③-a 從起點到最高處存在一條可通行路線（新增）

**量法**：`window.__probe.traverse(30)`。**不是目測、也不是用跳躍公式反推**——
真的跑 `update()` 迴圈 1800 幀（30 秒 × 60fps），控制的是一隻只會做兩件事的機器人：
**一直往右走**、**前方 150 內有比現在高 30 以上的平台左緣就按住跳躍鍵 0.3 秒**。

**門檻**：機器人要抵達模組最高的那塊平台（世界 y ≤ 356，平台頂 350，留 6 的容差）。

**這條抓到的第一個錯**：第一版機器人只按一幀跳躍鍵，
被我自己寫的「短按矮跳」截斷成 24 的跳躍高度，最高只爬到 832（地面是 880）。
**不是關卡不能過，是我的測試員不會玩。**

## ③-b 相機跟 Y：不抖、不越界（新增）

**量法**：`window.__probe.traverse()` 與 `camFollow()`，跑同一段路。

| 門檻 | 量的東西 |
|---|---|
| 相機垂直速度**反向次數 ≤ 全部幀數的 1%** | 抖不抖 |
| `max|camY − player.y| ≤ 260` | 越不越界 |
| 角色離開畫面的幀數 **= 0** | 有沒有跟丟 |

**抖動的量法改過一次，而且要說清楚**：第一版用 camY 的二階差分，量出 p99 = 5.92。
但**跳起來的時候相機本來就在加速**，二階差分量到的是真實運動，不是抖。
改成「相機垂直速度在連續幀之間反向、且兩邊幅度都 > 1」才算一次抖。

## ③-c 跳躍手感（設計值，寫死在這裡）

| 參數 | 值 | 意思 |
|---|---|---|
| `SPEED` | 330 /秒 | 走路速度 |
| `GRAV` | 1900 /秒² | 重力 |
| `JUMP_V` | 820 /秒 | 起跳速度 → **跳躍高度 176.9**，刻意略低於角色身高 180 |
| `JUMP_CUT` | 300 | 放開跳躍鍵時的最大上升速度＝短按矮跳 |
| `COYOTE` | 0.12 秒 | 離地寬容：踏空之後還能跳的時間 |
| `JUMP_BUF` | 0.12 秒 | 預輸入：落地前多久按跳都算數 |
| `CAM_LERP` | 7 | 相機跟隨速度（水平與垂直共用） |
| `CAM_LOOK` | 0.14（上限 130） | 下墜時相機往下預看，先看到要落在哪 |

關卡的抬升與缺口都對著這組數字設計：**最大抬升 120 < 176.9**、**最大水平缺口 80 << 285**（滿跳射程）。

## ④ 兩套配色（新增）

- **預設暗版**，按 `P` 或點右上角小方塊切亮版，**兩套共用同一份幾何**。
- **兩套都要各自跑完 ①-b／②／③，門檻一樣，不得因為「那是次要的那套」放水。**

### ②的量法在這裡壞過一次（必須記下來）
同一份幾何，遮蔽率暗版量到 **2.2%**、亮版量到 **22.2%**。
原因是舊的量法用「有前景 vs 沒前景」的色差判斷角色有沒有被蓋住——
而暗版的前景與角色都是近乎純黑，色差＝0，尺就回報「沒有被蓋住」。
改成拿「沒有角色但有前景」當參考幀（**跟兩邊各自是什麼顏色無關**），
兩套才量出同一個數字（21.9% / 22.0%）。
順帶也修了畫面本身：暗版的前景色原本是 `#0a060b`，那已經是純黑，
違反 ART_PIPELINE 的「純黑只給會動的」，改成 `#1a1119`。

# v4 增訂（2026-09-18）

## ①-c 垂直視差另外一組（新增）

水平係數維持 `[0.12, 0.38, 1.00, 1.55]`；
**垂直另外一組** `PARALLAX_Y = [0.02, 0.10, 1.00, 1.15]`。
用同一組的話「跳沒幾下大樓就在腳下」——遠處的東西在垂直方向本來就幾乎不該動。

**量法**：`window.__probe.vertParallax(530)`（530 ≈ 從最低跳到最高的 Δy），
**外加兩張真截圖**（同一個 x、相機一個在 880 一個在 350）做影像位移比對。

| 門檻 | 程式數字 | 截圖量到 |
|---|---|---|
| 層1 ≤ 畫面高 **3%** | 0.98% | **0.89%**（16px / 1800）|
| 層2 ≤ 畫面高 **10%** | 4.91% | **4.89%**（88px / 1800）|

**截圖比對這把尺自己壞過兩次，兩次都是我**：
1. 第一次直接比兩張圖的像素差 → 兩層都回報「位移 0」。
   因為**不動的天空佔了那一帶大多數像素**，把相關性壓到 0。
   改成比「每一列的水平邊緣強度」——邊緣只出現在剪影輪廓上，平滑的天空幾乎沒有值。
2. 改完還是 0。因為**我掃錯方向**：相機升高＝內容往下移，我卻往上找。
   改對方向之後才量到 16 / 88。
   **一把尺回報「0」的時候，要先確認它有沒有能力回報非 0。**

## ③-d 地形本身要有高低（新增）

浮空平台是輔助，**地面量體自己要有台地、走得上去的坡、塌陷下去的坑**——
人站上去是「踩在地上」不是踩一塊板。`TERRAIN` 那張表就是地形，
`groundTop()` 從它內插，看的與踩的同一條（ART_PIPELINE：不照圖描邊）。

模組內：`880 → 坡上去 770（台地）→ 880 → 塌陷 990 → 880`，後半段才是浮空平台。
③-a 的可通行判準沿用：機器人要從起點抵達最高處（**450**，含地形與平台）。

## ②的一次退步與它的真正原因（必須記下來）

中景改成廢墟結構之後，判準② 的最差取樣點掉到 **1.84**，而且 `p10` 也是 1.84——
**整個剪影幾乎每一個像素都是同一個亮度**，那代表角色整個站在一塊單色的東西前面。
反推 L ≈ 0.042，正好是 `midHole`。

原因不是「洞太多」，是**我把洞畫成更暗的一塊**。
真的被掏空的樓，大洞是**透光**的——從那裡看得到後面的天。
改成：**連成一片的大洞用透光色（比遠景稍暗），還完整的小窗維持暗色（室內）**。
最差取樣點回到 3.17，而且畫面也比較對。

> 前一次我在這裡是「猜」：先調洞的大小、再調洞的顏色，兩次都沒中。
> 這次是先把最差那一點畫出來、看 `p10` 跟 `median` 一樣 → 反推亮度 → 對到 `midHole`。
> **數字的形狀會告訴我它壞在哪，前提是我去看它的形狀，而不是只看它過不過。**

# v5（2026-09-18）：洞從「照窗格生成」改成「照結構開」

沒有新增判準，v1～v4 全部沿用、全部重跑。改的是中景的洞怎麼生成：

- 洞開在**兩片樓板之間的層帶**上（高度 = 一層樓減 13），不是照窗格長出來的
- 寬度**吃整層或半層**，邊緣**沿著核心牆或建築斷面切**（不是隨機的破洞連連看）
- **一棟最多 2 處**，而且兩個洞不相鄰
- **矮的樓（bh < 210）完全不開洞**——矮＝遠，距離越遠細節越少
- 窗維持小暗塊；被掏空的那一層不再畫窗

**這次沒有任何一條退步，而且不是巧合**：洞改成透光是 v4 就做完的事，
v5 只動「洞開在哪、多大、幾個」，沒有動亮度——
所以判準② 的最差取樣點、遮蔽、明度比、幀時間全部跟 v4 一樣或更好。
**先把「亮度」跟「位置」拆成兩次改，第二次就不會再把第一次的結論打翻。**
