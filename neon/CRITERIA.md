# 判準（動手之前寫死，2026-09-18，neon／賽博龐克夜街近戰原型）

改判準不是錯，**偷偷改才是**。任何一條要改，必須在 RESULT.md 明寫「改了什麼、為什麼」。

主角是**手感**，不是內容量。所以每一條都要回答「**它能分辨什麼**」，不是「要出現幾個」。

---

## ① 手機橫式效能
**量法**：`window.__probe.perf(frames)`，在 844×390 / DPR2 的 viewport 下跑，
相機沿關卡移動、敵人在場，記錄連續 ≥180 個 rAF 幀間隔（`performance.now()` 差）。
**門檻**：
- **p95 幀間隔 ≤ 20ms**
- 中位數 ≤ 17ms
- 另量繪製工作本身 `drawMs`：**p95 ≤ 8ms**（留一半預算給瀏覽器合成）

**能證明它錯的方法**：若 p95 只是被 vsync 綁在 16.7 而 drawMs 破表，就是我在自欺——兩個都要看。

## ② 打擊回饋量得到（這條是這個原型的主題）
每一項都先寫**設計值**，程式跑出來的**實測值**要對得上，對不上就是沒做到。

| 項目 | 設計值 | 量法 |
|---|---|---|
| 命中停頓 | 輕擊 **3 幀**、連擊第三下／重擊 **5 幀** | `__probe.feel()` 實際數「命中後遊戲邏輯被凍結了幾幀」 |
| 畫面微震 | 命中瞬間振幅 **9 世界單位**（重擊 16），**6 幀內衰減到 <1** | 量 `camShake` 每幀的實際偏移序列，取峰值與衰減幀數 |
| 敵人擊退 | 輕擊命中後 0.5 秒內水平位移 **≥ 90**、**≤ 260** 世界單位 | 命中後跑 30 幀，量敵人 x 位移 |
| 撞招牌噴火花 | 被擊退中的敵人撞到招牌／看板 → 產生 **≥ 12 個火花粒子**且該幀停頓 5 幀 | `__probe.feel().slam` |
| 連擊音 | 連擊 1/2/3 的音高**嚴格遞增**（頻率比 ≥ 1.05） | `__probe.audio()` 回傳三下的頻率 |

**它能分辨什麼**：分辨「有回饋」跟「只是扣血」。三項全 0 的版本也能通關——那就是失敗。

## ③ 關卡可通關，而且是手排的一段
**量法**：`__probe.bot(maxSeconds)` — 一隻只會「往右走／前方有坑或牆就跳／有敵人在攻擊距離就打／看到電閘就打」的
簡單機器人，用固定步長跑完整關；同時 playwright 用真觸控玩一段做截圖。
**門檻**：
- 機器人**能走到終點**（碰到 goal 事件），回報耗時。
- 全程耗時落在 **45～120 秒**之間（目標 60～90，留兩邊各一點餘裕；超出就是關卡長度沒排好）。
- `__probe.level()` 列出的事件表**順序固定、非程序生成**：起步空街 → 坑 → 兩直衝敵 → 高牆（需兩段跳）→ 電閘機關 → 三混合敵 → 小頭目 → 終點。
- **地形不可重複 Loop**：地形資料是一張有限的手寫表，`__probe.level().terrainFinite === true` 且關卡右端有牆（走不出去）。

**它能分辨什麼**：分辨「關卡」跟「地形產生器」。若機器人一路按右就過，或永遠走不完，兩種都不合格。

## ④ 角色在任何背景前都看得見（沿用 silho 的量法與門檻）
**量法**：`__probe.contrast(n)`，在整關均勻取 n 個點，各畫兩幀（有角色／無角色），
取角色剪影覆蓋像素，比 WCAG 相對亮度。
**門檻（不得放寬）**：
- 每點**中位數對比度 ≥ 3.0:1**
- **最差的單一取樣點 ≥ 2.5:1**
- 前景遮蔽：單張最大 ≤ 45%，**頭部遮蔽 ≤ 25%**，遮蔽 >25% 的點 ≤ 1/3

## ⑤ 美術規格的三條硬規矩（ART_PIPELINE 末段）
- 招牌／窗／管線等裝飾**一律裁進所屬建築輪廓**（程式上用 `clip()`，不是靠座標算準）。
- 地面基準線**以下填滿到畫面底**，相機下降不會露出天空底色。
- 光是**畫進去的固定色階**：不存在任何隨相機位置或光源方位改變物件外觀的程式碼。
  `__probe.staticLight()` 在兩個不同相機位置畫同一個世界座標的區塊，像素**必須完全相同**。

## 不在判準內（明說）
- 平衡、難度曲線、UI 美觀、音樂。這是一段手感試打。

# v2 增訂（2026-09-18，製作人試玩 v1 之後）

v1 的判準①②④⑤**全部沿用、門檻不得放寬**（③的時間門檻改為下面的④）。
v2 要回答的只有一件事：**「選對」有沒有回報。**

## ⑥ 無腦機器人不該過得了關
**量法**：`__probe.bots(n)` 跑 n=10 局，每局換一個亂數種子（敵人出手時機有抖動）。
「無腦機器人」＝ 只會「往右走／靠近就打／地形擋住就跳」（v1 那一隻，一個字都不改）。
**門檻**：通關率 **≤ 30%**（v1 是 100%）。

**它能分辨什麼**：分辨「我加了東西」跟「我加的東西真的改變了最佳解」。
若無腦機器人照樣 100% 過，那不管我加了幾個系統，玩家的決定還是一樣薄。

## ⑦ 會招架、會等預告的機器人要明顯過得比較好（**這條是核心**）
「會讀的機器人」＝ 同一隻機器人，加上三條規則：
敵人在預告 → 招架；敵人在架式 → 不打、等空門；自己剛揮空 → 不硬接。
**門檻**：
- 通關率 **≥ 70%**
- 且**比無腦機器人高至少 40 個百分點**

**它能分辨什麼**：分辨「難度變高」跟「選對有回報」。
兩隻都掉下去＝我只是把數值調難；只有會讀的那隻活下來，才代表新機制是一個**選擇**。

**能證明它錯的方法**：若兩隻差距來自「會讀的那隻剛好走得比較慢、少踩到東西」，
那就不是機制的功勞。所以同時記錄兩隻的**平均存活時間與被打次數**，差距要出現在「被打次數」上。

## ⑧ 招架成功必須是全場最強的回饋
**門檻（設計值，實測要對上）**：停頓 **9 幀**（輕擊 3、重擊 5）、時間放慢至 **0.35×** 持續 0.5 秒、
火花 **≥ 28 粒**、把敵人彈飛 **≥ 250** 世界單位（＝足以把人彈到招牌上，讓「瞄準」變可能）。

## ⑨ 揮空要有代價
**門檻**：揮空後不能動作的時間 **≥ 0.30 秒**（命中則沒有）。實測用探針量「揮空後到下一次出得了手的幀數」。

## ⑩ 敵人的預告要在剪影上看得出來
**門檻**：預告幀與待機幀，**角色剪影的像素重疊率 ≤ 80%**（＝形狀真的變了，不是只換顏色），
且預告長度 ≥ 0.35 秒（人看得到的一拍）。用 `__probe.telegraph()` 疊圖量。

## ④-v2 全程時間
會讀的機器人通關時間 **60～90 秒**，且**小頭目佔比 ≤ 35%**。

# v3 增訂（2026-09-18，冷讀沒過之後）

外部冷讀（另一組人，只看圖）判定 v2 的預告**沒過**：三種敵人只有 0～1 人讀成「要攻擊」，
主流讀法是「往前撲跳／特技動作」。同時抓到兩件更嚴重的：
**（a）guard 與 boss「正在出手」那一幀跟站立幀 md5 完全相同——根本沒有出手姿勢；**
**（b）boss 待機被三人一致讀成「伸手去摸招牌」。**
站立幀 0/9 被誤讀 → **尺是有效的，壞的是姿勢。**

## ⑩-v3 預告的判準補兩條（因為原本那個分數是靠位移賺來的）

v2 的重疊率 79% 有一半是「整個人往後移 30」換來的——形狀沒怎麼變，位置變了。
所以補兩條，把「形狀真的變了」跟「人走開了」分開：

- ⑩-a **武器尖端要高於頭頂 ≥ 40 px**（預告幀，畫面像素）。
- ⑩-b **剪影質心的水平位移 ≤ 10 px**（待機 → 預告）。整個人不准往旁邊移。
- ⑩-c 原本的重疊率 ≤ 80% 與預告長度 ≥ 0.35 秒**沿用**。

## ⑪ 出手要有自己的一幀
**量法**：`__probe.phases()` 對三種敵人各畫「待機／預告／出手／收招」四張剪影，兩兩比對。
**門檻**：四張**互不相同**（任兩張的像素差 > 2%），且傷害判定發生在**出手那一幀**（程式上驗）。

## ⑫ 冷讀重跑
改完找**全新的**子代理人（沒看過前一輪、沒看過這份文件）做開放題冷讀，
三種敵人的預告與出手各一張。門檻同前：**預告 ≥2/3 被讀成「要攻擊」；站立不得被誤讀**。
最多兩輪。

其餘判準（⑥⑦通關率與差距、②回饋、①效能、④可見度）**不得退步**。

# v4 增訂（2026-09-18，製作人實機回報「手機網頁卡成狗」）

**舊的①作廢。** 那個 p95 18ms 是 headless 桌機、手機尺寸量的，
而且 `drawMs` 量的是「下指令」的時間，不是「畫出來」的時間——
所以它可以一邊全綠、一邊在真手機上卡。

## ①-v4 CPU 節流下的幀間隔
**量法**：Chromium DPR2 / 844×390，CDP `Emulation.setCPUThrottlingRate` 設 4× 與 6×，
場景固定在**最激烈的一幕**（第二波三個敵人＋雨＋招牌落下），畫質檔位**鎖在最高檔**（不准靠自動降檔過關）。
**門檻**：**p95 ≤ 20ms、p99 ≤ 33ms**（4× 與 6× 都要過）。

**這條判準自己的限制（要明寫）**：
**CPU 節流是模擬，不是真機。** 它主要放大 CPU 端的工作，
而手機真正的瓶頸常常在 GPU 填充率、記憶體頻寬與瀏覽器合成，這些節流放大不到。
所以這條只能證明「CPU 這一側不是瓶頸了」，**不能證明真手機順**。真機要製作人再試一次才算數。

## ②-v4 分項計時
**量法**：`__probe.profile(frames)` 對每一層各自累計繪製時間。
**門檻**：沒有單一層在 6× 節流下超過每幀 2ms；且改前／改後的數字都要寫進 RESULT.md。

## 其餘判準
②回饋、④可見度、⑤固定光、⑥⑦通關率與差距、⑩⑪⑫姿勢與冷讀，**全部不得退步**。

# v5 增訂（2026-09-18）：進攻要變成一個決定

v3/v4 的結論：防守是決定了（等預告→招架→補刀），**進攻還不是**——會讀的機器人一局只揮空 1 次，
因為它根本不需要選招。這一輪只解這個。

**操作不加按鈕**：左半移動、右半攻擊、下滑招架、上滑跳，
第三個動作由**既有輸入組合**出來（右半往前滑／移動中攻擊＝突進斬）。

## 三種攻擊（設計值，實測要對得上）
| 招 | 怎麼出 | 起手 | 打擊距離 | 擊退 | 特性 |
|---|---|---|---|---|---|
| 快斬 | 右半點擊（原地） | 2 幀 | 92 | 0.55× | **打中「正在預告」的敵人＝打斷**（硬直 0.9 秒、傷害 1.6×） |
| 突進斬 | 右半往前滑／移動中攻擊 | 5 幀 | 124（並前衝 ~230） | 1.0× | **無視格擋**（破盾），拉近距離 |
| 重擊 | 連擊第三下 | 7 幀 | 140 | 2.2× | 慢、擊退最遠（把人推到招牌下） |

## 剋制關係（要能被機器人分辨出來）
- **直衝的**：起手時快斬打斷最划算（不打斷就只能招架或挨撞）
- **持盾的**：正面快斬／重擊會被擋下 → 突進斬破盾，或繞到背後
- **投擲的**：站遠打不到 → 突進斬拉近，或用重擊把他推去撞招牌

## 判準
三隻機器人，各跑 10 局（不同種子）：
- **無腦**（往右走＋靠近就打，v1 那隻）
- **只會招架**（v3 的那隻：等預告→招架→補刀，永遠只用快斬）
- **會選招**（依敵人種類挑招：直衝打斷／持盾突進／投擲拉近或推撞）

| 判準 | 門檻 | 為什麼是這個數字 |
|---|---|---|
| ⑬ 無腦機器人通關率 | ≤ 10% | 不得退步（v3 是 0%） |
| ⑭ 只會招架的機器人 | 通關率 ≥ 70%，**但平均時間 ≥ 會選招的 1.25 倍** | 「安全但慢」要真的慢得出來；1.25 倍是肉眼分得出來的差 |
| ⑮ 會選招的機器人 | 平均時間 **≤ 只會招架的 0.80 倍**，且**被打次數 ≤ 0.75 倍** | 兩條一起才算數：只快不安全，可能只是它比較躁 |
| ⑯ 全程時間 | **會選招的**那隻 60～90 秒 | 只會招架的那隻本來就該更慢，不受這條管 |
| ⑰ 效能 | 4×／6× 節流 p95 ≤20、p99 ≤33 | v4 判準不得退步 |
| ⑱ 回饋／可見度／姿勢 | 全部不得退步 | 同前 |
| ⑲ 冷讀 | 全新子代理人看連續截圖，開放題問「玩家在做什麼決定」，**要能說出他對不同敵人用不同打法** | 判準②③是機器人的語言，這條是人的語言 |

**能證明⑮錯的方法**：如果「會選招」只是因為它比較敢近身（攻擊次數多），
那它應該被打更多次才對。所以⑮同時要求**時間更短**與**被打更少**——
兩個一起成立才排除「它只是比較躁」這個解釋。
